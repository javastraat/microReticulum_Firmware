ScotMesh NomadNet Page Reference

Every page and API path a ScotMesh microReticulum node answers on its nomadnet destination, straight from ScotMesh.h — what each one shows, who can see it, and what it lets you do. Click a page to expand it.

Public Admin Settings Access Device Telemetry LXMF alerts JSON API

Public

Reachable by anyone who can hear the node — no identity or password needed, unless noted.

I /page/index.mu — Home

The node's landing page — whatever the operator has chosen to make public.

  • Node name, battery gauge (10-block bar, %, voltage, charge arrow)
  • Uptime, path count (links to Routes), radio freq/SF, live airtime %, operator note
  • "Admin" link if you're already registered, or "Register" if password sign-up is on
  • Verified-identity line, firmware + board footer

Visitor view is configurable on the Settings → Home page.

r /page/r.mu — Routes

The node's path table: destination hash · hop count · last heard, 10 rows per page, short or full hash display.

b /page/b.mu — Neighbours

Peers this node has heard announce: destination hash · time since heard · name, paginated.

l /page/l.mu — Register

Request admin access with a password, if the operator has turned registration on. Goes straight to admin, or into an approval queue, depending on operator setting.

3 wrong tries locks you out for 15 min; 10 wrong tries mesh-wide pauses registration for an hour.

Admin

Reachable only once your identity is on the admin list — everyone else lands on an "Admins only" page instead. This is where the Home page's own "Admin" link goes.

a /page/a.mu — Admin hub
  • Node name, battery %, uptime
  • Your current link: hop count and signal, and the last-hop relay's name if more than one hop away (by path table, or guessed from signal)
  • Verified-identity line
  • Live banners when relevant: an in-progress radio trial awaiting confirmation, or a count of registrations waiting for approval
  • Menu into Settings / Access / Device / Telemetry / History (the last two only on boards built with them)

Settings

Reachable only once your identity is on the admin list — everyone else lands on an "Admins only" page instead.

s /page/s.mu — Settings hub

Menu into the six pages below, each with its current value shown inline.

n /page/n.mu — Name & announce
  • Node name (32 chars), operator note (22 chars)
  • Announce interval: 30m / 1h / 3h / 6h / 12h
  • Renaming re-announces the node immediately
  • Flag (2-letter country code, e.g. NL, shown as 🇳🇱) and Footer text (24 chars): an optional line of your own on the home page, just above the 🏴󠁧󠁢󠁳󠁣󠁴󠁿 ScotMesh microReticulum credit — e.g. 🇳🇱 Reticulum Amsterdam. Leave both empty for no extra line. Stored in its own file, so older settings are untouched
h /page/h.mu — Home page
  • Checkboxes for what a visitor sees: battery, uptime, radio, paths, airtime, operator, routes-link
  • Telemetry API on/off switch
  • "Preview" link — see the visitor view live
g /page/g.mu — Map (rmap.world)
  • Paste a coordinate (lat, lon) + height in metres
  • Exact or ~1 km-rounded precision, publish on/off
  • Last-sent time once published, "Announce now" action
f /page/f.mu — Radio
  • Current frequency, bandwidth, SF, CR, TX power
  • Two one-tap presets: ScotMesh 868 / 433

5-minute reversible trial — auto-reverts unless you hit Keep.

w /page/w.mu — Role
  • Fixed relay · Access point · Mobile · End device
  • Relays forward traffic for others; end devices never do

Needs a restart to apply.

y /page/y.mu — Power
  • Battery-% threshold (5–60%), action below it: lower TX to 10 dBm, radio off until charged, or nothing
  • Separate hard cutoff: radio off below 3.3 V
  • Live flag if a limit is currently in effect

Access

c /page/c.mu — Access hub

Menu into Admins / Password / Change log, each with a live count.

k /page/k.mu — Admins
  • Up to 8 admin identity hashes, your own row marked "you"
  • Add by pasting a 32-hex identity hash
  • On nodes with LXMF alerts: key after an admin means the node has their public key and can send them alerts

Removing an admin is confirm-gated; you can't remove the last admin.

p /page/p.mu — Password registration
  • On/off, and "needs approval" (routes new sign-ups into a queue instead of auto-admitting)
  • Set/change password (8+ chars) — salted + hashed, never stored in plain text
  • Outcome of the last registration attempt
j /page/j.mu — Change log

Last 32 admin actions: how long ago, what happened, which identity.

q /page/q.mu — Waiting for approval

Only reachable when "needs approval" is on. Shows pending registration requests and how long they've waited; approve or deny each.

Device

d /page/d.mu — Device hub

Menu into the five pages below.

e /page/e.mu — Health
  • Free RAM / flash, uptime, boot count, last reset reason
  • Radio noise floor, last RSSI/SNR, current + average airtime %
  • Packets rx/tx, path/announce/known-destination/link/neighbour table sizes
i /page/i.mu — Lights & Bluetooth
  • LED mode: on / off / first 10 min only — errors always show regardless
  • "Blink for 30s" locator action
  • Bluetooth on/off, "unpair all paired phones" (where supported)
o /page/o.mu — Logs

Last 5 log lines, with a refresh action.

x /page/x.mu — Maintenance

"Announce now", auto-restart schedule: off / daily / weekly.

Confirm-gated resets: clear routes & data, factory reset, full reset.

m /page/m.mu — Restart & update
  • Restart (confirm-gated, ~15s offline)
  • nRF52: Bluetooth DFU or USB-bootloader window — ESP32 (with a spare app slot): 20-min WiFi update AP ScotMesh-Update with a one-time password; upload the .bin at http://10.73.73.1, with a progress bar

Needs battery ≥30% or charging; one-time 2-minute confirm token.

u /page/u.mu — About

Firmware tag, board name, transport/management/NomadNet/probe destination hashes, and on nodes with LXMF alerts the node's LXMF address (the one to add as a contact).

Telemetry

Only on boards built with them. Telemetry needs HAS_ENV_SENSORS (Solar Node P1). History needs SM_HISTORY (Solar Node P1, Heltec V3, Heltec V4). On boards without an environment sensor, or without an MCU temperature reading (the Heltecs), those History lines are simply left out.

t /page/t.mu — Telemetry

Auto-detected Grove environment sensors: an M5Stack ENV unit — ENV I (DHT12+BMP280), ENV II (SHT30+BMP280) or ENV III (SHT30+QMP6988) — or a single module with an SHT4x, SHTC3, AHT10/20, BME280, BME680, BMP280, BMP180/BMP085 or LPS22HB. With several, humidity comes from the best humidity chip (SHT4x, SHT30, SHTC3, BME680, BME280, AHT, DHT12, in that order), pressure from the best pressure chip, and temperature from the humidity chip. The BME680’s gas (air quality) reading is not used.

  • Temperature, and humidity if a humidity sensor was found
  • Pressure + calculated altitude if a pressure sensor was found
  • Which exact chips were detected (e.g. "SHT30 + QMP6988")
  • Power monitors on the same Grove port, if fitted: INA219, INA226, INA260 or INA3221 (up to two chips, four readings). One line each with volts, milliamps and watts, e.g. INA226 13.12V 412mA 5.41W; an INA3221 shows its inputs as INA3221/1–/3, and inputs with nothing connected are left out. Current is worked out for a 0.1 Ω shunt, as on the usual breakout boards (build flag ENV_INA_SHUNT_OHMS for others). Negative current means it flows the other way, e.g. into the battery
  • MCU die temperature, read directly off the nRF52840
  • With more than one sensor chip, a line per chip with its own readings at the bottom, e.g. SHT30 21.3C 54% and QMP6988 21.8C 1012.4hPa. Handy with a second sensor in another place (inside the box, outside). These lines are left out if the page would not fit in one packet
  • Says plainly if nothing is attached, or the read failed
z /page/z.mu — History

Battery, sensor and mesh readings over the last 7 days. Linked from the Admin hub.

The node takes a reading every 10 minutes and saves the average of each hour as one record. It keeps the last 7 days (168 hours) in its flash memory, so they survive restarts.

The first reading is taken 1 minute after start. Until the first hour is saved, the page shows the hour so far: how many readings, and their averages.

A record is only saved once the node has run a full hour. If the node keeps restarting every few minutes (for example on an almost empty battery), it saves nothing, so the week already stored is not pushed out by short runs.

  • A small bar chart of the battery over the last 24 hours, one bar per hour, oldest on the left. An amber | marks a restart. The node can't tell how long it was off, so the bars continue right after it
  • Battery now, the lowest and highest of the last 24 hours, and the biggest drop while not charging (e.g. -14%/11h: 14 % lost over 11 hours, typically overnight)
  • Battery min–max for each of the last 7 days, newest first
  • Sensor temperature 24 h and 7 d min/max, MCU temperature, humidity range and the pressure trend
  • Neighbours and routes now, and the most neighbours seen in the last 24 hours
  • The page must fit in one LoRa packet. If it would be too long, the lines at the bottom are left out; the battery lines at the top always stay

LXMF alerts

Only on boards built with SM_LXMF — Solar Node P1, Heltec V3 and Heltec V4. The node gets its own LXMF address, so it shows up in Sideband, NomadNet or MeshChat like any other contact, under the node name. It announces that address together with its NomadNet page, on the same interval. The address is also on the About page.

  • “Running again” alert: 2 minutes after every restart, all admins get a message saying the node is running again, why it restarted, how many restarts so far, and the battery level. On the Solar Node P1, a crash (hard fault or uncaught exception) is in it too; the Heltecs give the reset reason only. Example: Hilltop is running again (watchdog, restart #12, hard fault pc=0002a1f4), battery 64%
  • “Battery low” alert: sent once when the battery, while not charging, drops below the Power page threshold plus 10 %. That way you hear about it before the Power page lowers the TX power or turns the radio off. Example with a 25 % threshold: at 34 % you get Hilltop battery low: 34% 3.61V, not charging. You only get it again after the battery has charged back up to 45 % (or starts charging) and then drops again
  • Commands from admins: send status for battery, uptime, neighbours, routes, temperature and any power monitor readings; anything else gets a short help reply. Messages from anyone else are ignored, and so are messages that can't be verified as really coming from that admin (their signature doesn't match)
  • Keys: the node needs an admin's public key to write to them. It saves it when the admin opens any page while identified (the Admins page then shows key next to them); otherwise it uses the admin's own LXMF announce if it has heard one
  • Delivery: each alert goes out as one encrypted packet straight to the admin's LXMF client. If the node doesn't know a route to the admin yet, it asks the mesh for one first
  • When the admin is offline: the node keeps trying for 10 minutes, then gives up on that alert. It doesn't use a propagation node (an LXMF mailbox that holds messages until you're back), so an alert sent while your client is off is missed
  • Stamps: some clients have an anti-spam setting that requires unknown senders to add a “stamp” (a small proof of work). The node doesn't make stamps, so with that setting on, its alerts are silently dropped. Turn the setting off, or mark the node as a trusted contact if your client allows that
  • Message time: the node has no clock, so it takes the time from page requests and incoming messages, and saves it hourly. After a restart, messages carry the last saved time until it hears a new one

JSON API

Same destination as the pages above, plain JSON replies — for scripts and dashboards rather than browsing. Toggled by the Telemetry API switch on the Home page settings.

Generated from ScotMesh.h in microReticulum_Firmware. Admin pages require being on the Admins list (/page/k.mu) or registering with a password (/page/l.mu) — everyone else sees "Admins only."
